# paseo-status

Paseo plugin: agents publish where their work stands via one MCP tool (`status_set`); Paseo shows it as a card per agent, with staleness and a Refresh button.

## Layout

- `index.server.ts` wires everything. `server/`: `store` (one JSON per workspace, keyed by agent; counts turns since the last update), `service` (the MCP tool, agent instructions, refresh steered into a running turn when the provider can, else held until the turn ends, automatic refresh of stale cards on panel open, `paseo-status` reply-block fallback for agents created before install, read-only view of the asks plugin's open asks), `equipped` (agents created while installed, so they have the tool), `bridge` (stdio MCP script written to the data dir), `listener` (localhost HTTP the bridge calls), `agents` (agentId → workspaceId; caller by cwd for Codex), `permissions` (which tool prompts to auto-allow).
- `client/` + `index.client.tsx`: React Native only (runs on mobile). Colors from `theme.colors`.
- `client/RowBadge.tsx`: the sidebar workspace row badge (needs you / working / done) from `status.summary`, which `summarize` in `shared/status.ts` computes from cards, open asks, and live agents. Registered only when the host has `addWorkspaceRowItem` (newer than SDK 0.12, typed locally until the SDK ships it).
- `client/summary.ts`: one workspace summary item per workspace with a card (Overview tab label, the newest card as `status` for the FSH Overview's Status section (with the newest `goal` any card in the workspace has, via `workspaceOverviewStatus`), with `answered` from `isAnswered` like the Status tab, and `workState` for Paseo's agent-reported sidebar grouping, computed on the server by `workspaceWorkState` in `shared/status.ts` and returned by `status.list` when asked with `withWorkStates`). Never sets `needsYou` (a card waiting on the human reports `workState: "waiting"`, a blocked one `"blocked"`), so it never opens Explorer.
- `server/liveness.ts`: what backs a `working` card (`workspaceWorkState` holds Working only while something does) (the agent running, its workspace shown as running, its background work, or a descendant agent by `paseo.parent-agent-id` label, in any workspace, that is), when live work was last seen (5 min grace), and the one wake-up prompt a minute after an idle parent's last live child stops (for `working` and `blocked` cards), unless something woke the parent first. For an idle agent's `waiting_on_you` card it lists `liveChildren` (descendants live in other workspaces); `withLiveChildren` in `shared/status.ts` reads such a card without an open ask as blocked on them, for the grouping, `status.list` with `withWorkStates` (the Overview) and, via the last pass's cache, `status.summary` (the row badge). In memory: lost on reload.
- `server/snooze.ts` + `needsYouSince` in `shared/status.ts`: after a `status_set` call or a turn end, reports each snoozed workspace whose card turned `waiting` or `done` after the snooze began (never `blocked`) (`workspaces.ref(id).reportNeedsYou({ agentId })`, FSH hosts with `features.workspaceAttentionReport`). The host decides from its snoozed-workspace setting whether that wakes it, and announces the agent's quiet finished turn. A workspace snoozed while it already needed you stays snoozed.
- `server/blockers.ts`: resolves a blocked card's `blockedBy` (PR via `gh pr view`, cached `PR_CACHE_MS`; agent by id or unique prefix; workspace by id) into display rows, falling back to the raw ref. `status.list` returns them as `blockers` per agent; `overviewStatus` passes them to the Overview as `blockedBy` only while the card is blocked.
- `client/chat-cards.tsx` + `shared/settings.ts`: the chat card, its timeline transformer and the host-scoped Chat setting (`collapsed` by default, `expanded`, `hidden`). The renderer collapses live from `useSettings`. Hiding happens in the transformer, because a renderer that draws nothing still leaves its row's gap. Paseo caches transformer output per row, so a change to or from `hidden` registers the transformer again to redo rows already shown.
- `shared/status.ts`: Zod schemas and RPC contracts. `shared/timeline.ts`: turns a completed `status_set` tool row into an inline chat card (snapshot from the call's input; live when it still matches the stored status). `paseo-status` reply blocks are not transformed: transformers emit only plugin items, so it would mean replacing the whole reply.
- `preview/`: own package.json; renders `client/` with react-native-web and mocked host modules for the README screenshots (`docs/*.png`). Not shipped.
- `bridge`, `listener`, `agents`, `permissions` and `host-sdk` are copied from `paseo-asks`. Fix a bug in one, fix it in both. The status bridge also sends its agent ID with `/tools` and `/instructions`, which the asks bridge doesn't need.

## Load-bearing facts (Paseo 0.12)

- Helpers (agents with the `paseo.parent-agent-id` label) get no tool or card. `before("agent.create")` sees only `config` and `env`, not labels, so the MCP server can't be left out: the bridge sends its agent ID to `/tools` and `/instructions`, and helpers get an empty list. Old helper cards stay on disk and are filtered by live labels (`visibleCards` in `index.server.ts`). A helper detached by a handoff loses the label but keeps its empty tool list until its session restarts.
- Background workspaces (`workspace.background`, e.g. Inbox runs before the human opens them) get no status cards: `status_set` returns `BACKGROUND_SKIP` and stores nothing, and Refresh all skips them. The tool stays, because an agent's tools are fixed at creation and the human may take the run over.
- The stdio bridge inherits `PASEO_AGENT_ID` from the agent process; that is how a tool call knows its caller. Codex drops it on Paseo hosts before fullstackhouse/paseo#98, so the bridge also sends its cwd and `pickCaller` picks the running agent there, skipping providers that send their own ID (`COMPAT(codex-agent-id)`).
- `agent.turn_ended` carries no history: its `timeline` has been empty since Paseo 0.15 (getpaseo/paseo#7477). Read the turn with the host's `latestTurn` (`@getpaseo/plugin/server`, FSH hosts from `0bd77c5`; typed locally in `server/host-sdk.ts` until the npm SDK has it).
- `agents.ref(id).send()` with `activeTurnBehavior: "steer"` joins a running turn only when `capabilities.supportsSteering` is set; otherwise it interrupts, so Refresh waits for `agent.turn_ended` there.
- Plugin server code cannot write settings, so clients poll (`POLL_MS`).
- Claude plan mode prompts even for preapproved MCP tools, and Codex asks to approve every MCP call (`CodexMcpElicitation`); the server auto-allows both for the status server.
- Codex (0.166) defers every MCP tool behind its tool search, with the server instructions only in the deferred descriptions; `alwaysLoad` works for Claude only. Without the host telling Codex to look them up, Codex agents never call `status_set` on their own.
- `before("agent.session_open")` can change env only, not MCP servers: agents created before install never get the tool, hence the reply-block fallback.
- `useAgent`/`useWorkspace` throw outside a workspace panel (screens, popovers): names come from the server in `status.list`. The preview mocks don't provide them, so a regression fails there too.
- Background work is `agents.ref(id).backgroundWork.list()` on FSH hosts only (feature-detected in `server/liveness.ts`). Provider subagents (Claude background Task agents) have no plugin API: the only sign is the host showing the agent's workspace as `running`, which also covers any other agent running there. Heartbeats and schedules are not reachable at all.
- `create_agent` from an agent notifies the parent when the child finishes (`notifyOnFinish`, default on, ~2 s later). The plugin's wake-up waits `WAKE_DELAY_MS` so that notification goes first and cancels it.
- Plugin RPC names must match `/^[a-z][a-z0-9._-]*$/` (no camelCase).
- Reads `~/.paseo/plugin-data/asks/workspaces/*.json` for open asks; never writes there.

## Commands

- `npm run typecheck`, `npm test`.
- `npm run e2e`: real Paseo daemon (the FSH CLI bundle that `e2e/fsh-host.mjs` downloads by tag and sha256 before each run, since the plugin needs FSH-only host exports; `e2e/` pins Claude Code and Codex) in a temp `--home` and `HOME`, plugin installed, agents answered from `e2e/cassettes/` by a local proxy: Haiku via `ANTHROPIC_BASE_URL` (Messages API), Codex `gpt-5.6-luna` via a `model_provider` in the sandbox's `~/.codex/config.toml` (Responses API over HTTP/SSE). No network, runs in CI. `unprompted.e2e.ts` gives an ordinary task that never mentions status and expects a card anyway: the other scenarios tell the agent to call `status_set`, so they only test the wiring. `PASEO_HOST_SRC=<paseo checkout>` (built with `npm run build:server`) runs on that checkout instead of the pinned tag. The pinned tag must include Paseo's note telling Codex to look up deferred MCP tools, or the Codex unprompted case publishes no card. After changing a scenario or anything the model sees (instructions, prompts, tool output), re-record: `npm run e2e:record` with `OPENROUTER_API_KEY` in the env or `e2e/.env` (the proxy adds it; agents only see a dummy key), then commit the cassette. A replay miss fails the run and lists the unmatched request. `e2e/proxy.ts` and `e2e/fsh-host.mjs` are shared with `paseo-asks`: keep them self-contained and copy changes across.
- Refresh an agent from a terminal: POST `/refresh` `{"agentId": "..."}` on the port in `~/.paseo/plugin-data/status/server.json` with its bearer token.
- After edits: `paseo plugin reload paseo-status`, then `paseo plugin ls` must say `running`; logs via `paseo plugin logs paseo-status`. Never restart the daemon.
